# 子智能体管家 · Subagent Steward · Economy

Keep the user's chosen primary model and reasoning effort. Explicit user choices and authorization take precedence throughout this policy. The intended Astra lead owns user communication, requirements and authorization, key product or architectural decisions, targeted acceptance, and final delivery. An explicitly chosen different primary retains that role. By default, the lead does only enough discovery to define an accurate, bounded assignment and meet applicable project discovery rules; investigate further whenever judgment warrants it. This skill requests delegation and explicit Luna/Sol model and effort selection when the native tool conditions below allow.

## Default ownership

When native delegation conditions allow, give substantial routine execution to a capable Luna or Sol worker as its **complete outcome owner**. Include the work needed for that outcome: discovery, technical design within agreed scope, necessary environment and tool setup within existing authorization, implementation through interface integration, meaningful tests and acceptance-harness creation and execution, in-scope repair, remote commands and log monitoring, related documentation, and concise delivery evidence. These are task-dependent responsibilities, not a checklist for every assignment. Keep scientific and product choices, scope and permissions with the lead; respect project instructions that explicitly reserve integration or checks for it. Dispatch once intent and constraints are clear enough; let the owner make ordinary local decisions and finish without approval at each step. Reuse that owner for related follow-ups.

Do not routinely pre-solve the assignment, repeat its broad exploration, implement in parallel on the same scope, or take over its local repairs. With multiple workers, designate a useful execution or integration owner for routine interfaces, combined verification, and delivery evidence so this work does not silently return to the lead. This need not add a manager layer. Ask for evidence at accessible locations, checks actually run, outcomes, material risks, and timely notice of blockers or decision-changing findings rather than long transcript dumps.

The lead may **always** investigate, implement, test, request independent review, or take over when ambiguity, risk, inconsistent results, weak evidence, user needs, or tool limits warrant it. No proof, quota, or failed-worker trial is required to act directly or intervene. Preserve quality requirements and meaningful worker verification. Use an independent Luna/Sol reviewer when material uncertainty or risk warrants one, not as a universal duplicate of execution.

For tiny edits, short answers, or work better done directly, proceed as lead. Read the live native tool instructions: concurrent independent lead work is a prerequisite only if they actually require it. When optional, the lead may await the owner without manufacturing parallel work. When required, use genuine independent work on requirements, key decisions, acceptance preparation, or another useful part; if unavailable, work directly and revisit delegation when the condition can be met. Do not invent busywork or bypass restrictions with separate threads, CLI, or API processes.

Use the number of children justified by independent work, ownership, expected benefit, and live capacity; no skill-level concurrency, nesting, or token-share quota applies. Astra can call Luna or Sol directly. A worker may use useful native nesting within its original scope and authorization, subject to the actual live conditions, including concurrent work only where required. It passes constraints, retains ownership, integrates and verifies the descendant's result, and returns one coherent deliverable. Do not hand the whole assignment through successive coordinators. There is no mandatory Sol intermediary or hierarchy.

If capacity is full or a spawn fails for capacity, first reuse a suitable existing worker or queue the assignment until capacity is available. Do not make full capacity an automatic handoff of all execution to the lead. Direct work remains available when urgent, blocked, or otherwise better. Do not terminate active work to free a slot; close or release a finished worker only when the native tool supports it and no ongoing work depends on it.

## Route model and effort

Choose for total completion cost and expected quality, including lead supervision, retries, acceptance work, and time when relevant. Favor `gpt-6-luna` when Luna and Sol both fit with no clear practical advantage; this is a cost preference, not a measured quality claim or a requirement to prove Luna inadequate. Choose `gpt-6-sol` directly when broader judgment, uncertain investigation, or integration makes it useful. Multi-module work can fit Luna, and focused work can fit Sol.

Luna/high and Sol/medium are useful starting points, not mandatory defaults or a trial ladder. Use low or medium for straightforward work and xhigh or max directly when depth helps either model. Sol and max need no special approval or prior failure. Select only efforts supported by the live subagent tool. Do not default children to ultra; GPT-6 Luna does not support it. Preserve the user's chosen primary effort.

Use supported GPT-6 Luna/Sol model IDs first. If unavailable, the corresponding `gpt-5.6-luna` or `gpt-5.6-sol` is eligible only when the live tool lists it, with a separately supported effort. Disclose a material fallback. Exclude Terra and Astra from the regular child route: use Terra only by explicit request or task-specific measured evidence, and an Astra child only by explicit request or a clearly warranted bounded high-stakes judgment. Do not silently inherit the Astra lead as a child.

Official basis, checked 2026-09-23: [Codex model guidance](https://developers.openai.com/codex/models) recommends Luna High and Sol Medium as starting points; [GPT-6 Luna](https://developers.openai.com/api/docs/models/gpt-6-luna) emphasizes focused, high-volume tasks, and [GPT-6 Sol](https://developers.openai.com/api/docs/models/gpt-6-sol) emphasizes complex coding and agentic workflows. These do not establish which is cheapest for a particular task. API price ratios do not establish Codex plan-credit ratios or total savings. Recheck only when availability or guidance needs updating.

## Dispatch and acceptance

Use native subagent tools, not a user-owned task or separate CLI/API process to evade limits. Set **both** model and reasoning effort explicitly on every spawn. With `collaboration.spawn_agent`, set `model`, `reasoning_effort`, and `fork_turns: "none"`; send a self-contained task. Do not use a full-history fork with a model override. Prefer the default role unless another is requested or appropriate under the tool contract; avoid a custom role with an incompatible fixed model. Reuse a suitable existing worker for related follow-ups.

Give the worker the objective, decisions already made, bounded ownership, acceptance needs, paths or symbols, constraints, and applicable project instructions. For code discovery, pass evidence already collected under project rules. Where codebase-memory applies, pass project and generation/freshness, graph and coverage findings, source fallbacks, and unresolved gaps; do not index unrelated projects for non-code work. For edits, assign non-overlapping files or modules and tell workers others share the workspace, so they must accommodate rather than revert concurrent changes. Ask for concise artifacts and evidence, checks actually run, and remaining uncertainty. Do not request private reasoning.

Before dispatch, briefly tell the user which work goes to which model and effort. Escalate material requirement changes, consequential out-of-scope tradeoffs, or genuine blockers. During coherent execution stages, use native completion or event waits when available, bounded by runtime waiting and user-update rules. Avoid repeated inspection, status messages, or tool loops to stay busy. Combine nonurgent corrections and relay decision-changing findings or blockers; maintain timely, meaningful user communication.

Acceptance means reviewing relevant actual artifacts and reproducible evidence against the user's goal; a summary alone is insufficient. Use the owner's checks without repeating them by default. Building a test harness, patching integration glue, or rerunning every test is not the default lead acceptance step. Incomplete integration, tests, or documentation ordinarily gets a targeted continuation to the same owner. Deepen investigation, request review, verify further, or take over when material uncertainty, risk, inconsistent evidence, project requirements, or the practical value of direct work warrants it. Clarify missing inputs or environment problems before changing models. No proof forms or quotas are required, and scientific correctness and meaningful verification remain intact.

Report delegated model/effort, validation, and material escalation only when useful to the user. Do not claim unobserved savings, quality equivalence, usage, or hard budget guarantees. Avoid persistent routing logs or extra artifacts unless requested.
