# Model guidance and policy basis

Official sources checked 2026-11-14:

- [GPT-6.1 Terra](https://developers.openai.com/api/docs/models/gpt-6.1-terra) is described as fast and efficient for visual reasoning, precise computer use, and clear, natural writing, including photos, technical drawings, application screens, and drafting or revising text.
- [GPT-5.6 Terra](https://developers.openai.com/api/docs/models/gpt-5.6-terra), model ID `gpt-5.6-terra`, is designed to balance intelligence and cost and roughly corresponds to the earlier GPT-5 mini tier. Its existence supports a family fallback candidate, not identical capability to 6.1 Terra or availability in the current native tool.
- [GPT-6.1 Sol](https://developers.openai.com/api/docs/models/gpt-6.1-sol) covers complex coding, computer use, and professional work.
- [GPT-6 Luna](https://developers.openai.com/api/docs/models/gpt-6-luna) is positioned for efficient focused, high-volume work.
- [Model selection](https://developers.openai.com/api/docs/guides/model-selection) includes bounded problem-solving for Luna and deeper reasoning on clear constraints at higher effort. It suggests Terra for writing from supplied material, computer use with a defined outcome, and scoped code fixes. Sol covers complex technical and professional projects, coordinated deliverables, and judgment from conflicting evidence. These recommendations overlap; clear task boundaries alone do not determine the model. The guide's representative-task comparisons can inform policy tuning without becoming a benchmark requirement before each dispatch.
- [Codex subagents](https://learn.chatgpt.com/docs/agent-configuration/subagents) explains inherited model/effort unless explicitly set, possible custom-agent overrides, inherited skills and permissions, and the potential for delegation to increase total tokens. Its task guidance distinguishes demanding, ambiguous multi-step work from narrowly scoped, clear, repeatable work.
- [Codex skills](https://developers.openai.com/codex/skills.md) supports bundling scripts with a skill. A client may not have a compatible runtime to execute an attached script, so the skill must provide a truthful fallback.

The API pages list `low`, `medium`, `high`, `xhigh`, and `max` for these models; Luna and both Terra versions also list `none`. Their API default is `medium`. These lists do not establish what a particular native Codex tool supports. Client guidance includes Luna/high and starting Sol from the supported client effort; consult current guidance when it matters.

The skill's root-family boundaries (Astra and Sol may use Luna/Terra/Sol, Terra may use Terra/Luna, and Luna may use Luna), per-primary delegation tendencies, and Sol-policy routing fallback for missing or unreadable primary identity are project policy. The fallback does not assert that the root is Sol or change its selected primary or effort. Favoring Luna when permitted candidates are equally suitable, family fallback routes, bounded nesting permission, complete-outcome ownership, and effort starting points are also project policy. These rules are not official defaults, an objective capability ranking, exclusive jobs, measured quality equivalence, or savings guarantees. User instruction or existing explicit authorization can widen a root's family boundary; descendants and custom roles cannot widen it on their own.

Use the live tool's supported models, efforts, role behavior, permissions, capacity, and waiting rules. Supported-model lists identify available children, not the current primary. When explicit current-turn primary metadata is absent, the root uses the bundled [reader](primary-model.md) to resolve its exact current session through read-only local state and bounded `turn_context` metadata. The reader requires Python 3.9+ and standard-library modules; bundled PowerShell and POSIX launchers discover a compatible PATH runtime or accept an explicit existing Python path. If a client offers a bundled-runtime discovery tool, it may be used once after launcher discovery fails. This route was verified locally on 2026-11-14; the SQLite and log schema are local implementation details, not a stable public OpenAI API. Unavailable runtime or unsupported metadata falls back to Sol routing policy without changing or inventing the primary model. Workers inherit the root's routing boundaries instead of performing that lookup. Instructions express behavioral boundaries but do not create separate sandbox enforcement. No recursive chat-history scan, benchmark prerequisite, mandatory hierarchy, or price table is needed for ordinary routing.
